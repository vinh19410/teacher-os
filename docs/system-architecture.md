# System Architecture

Cô Mỹ Dạy Tiếng Anh (teacher-os) is a monorepo: a unified LMS gateway Worker (`apps/lms`) composing the React teacher web app (`apps/web`), student portal (`apps/student`), and admin console (`apps/admin`), static profile/landing sites (`apps/profile`, `apps/landing`), a Hono server (`apps/server`), and shared packages for API contracts, persistence, and deployment wiring. The runtime contract is snapshot-driven: the browser reads a kernel snapshot, sends POST commands, and refreshes the snapshot after each write. Browser E2E coverage lives in [apps/e2e/playwright.config.ts](../apps/e2e/playwright.config.ts), which boots the real server app under Node against a fresh local D1 database so these flows run without Cloudflare credentials.

## Current request flow

1. Production runs on `APP_DOMAIN=msmy.io.vn`; staging stays on `staging.teacheros.io.vn`. On staging, apex and www are served by the static landing page Worker (`apps/landing`, via `Cloudflare.Website.StaticSite`); on prod landing has no custom domain because the apex belongs to the profile site. Requests to the teacher profile site (`msmy.io.vn` / `www.msmy.io.vn` on prod, `profile.<domain>` on staging) are served by the `profile` StaticSite Worker (`apps/profile`). The unified LMS gateway (`apps/lms`) lives at `lms.<domain>` — serving `/login`, `/pay/:token`, `/teacher/*`, `/student/*`, and `/admin/*` with legacy 301 aliases `app.<domain>`, `student.<domain>`, and `admin.<domain>` — and the API lives at `api.<domain>` (see [packages/infra/src/topology.ts](../packages/infra/src/topology.ts)).
2. The auth route in [apps/web/src/routes/_auth/route.tsx](../apps/web/src/routes/_auth/route.tsx) blocks unauthenticated users and sends them to login.
3. [apps/web/src/lib/data-provider.tsx](../apps/web/src/lib/data-provider.tsx) subscribes to the shared TanStack Query `['kernel']` entry (`GET /api/kernel`) and waits for it before rendering children; kernel writes refetch that same entry through the command bus.
4. [apps/web/src/lib/repos/kernel.ts](../apps/web/src/lib/repos/kernel.ts) maps UI actions to POST requests and maps kernel snapshots into the legacy UI shape.
5. [apps/server/src/app.ts](../apps/server/src/app.ts) installs CORS, the bootstrap middleware, and the `/api` router chain.
6. [apps/server/src/routes/kernel.ts](../apps/server/src/routes/kernel.ts) enforces origin and JSON checks for POSTs, then executes org-scoped reads and writes.
7. [apps/server/src/routes/snapshot.ts](../apps/server/src/routes/snapshot.ts) assembles the snapshot from the canonical database tables.
8. [packages/db/src/schema/index.ts](../packages/db/src/schema/index.ts) is the persistence owner, and [packages/api/src/contracts.ts](../packages/api/src/contracts.ts) is the wire contract owner.
9. [packages/api/src/skeleton.ts](../packages/api/src/skeleton.ts) owns occurrence-identity math (schedule skeleton, `conforms()`, offline backfill planning — issue #98); apps/server consumes it for generation, apps/web never re-implements it.

## Architectural rules

- Keep teacher kernel org scoping on the server; do not move it into client headers.
- Keep the bootstrap rule idempotent so a new authenticated teacher always lands in a usable workspace.
- Keep the snapshot contract stable for the web adapter; if the server shape changes, the adapter and contracts change with it.
- Keep scheduled lesson actions separate from curriculum lessons.
- Keep entitlement state on `session_package` owned by `student`; the package is always created attached to an `enrollment` — either with the student (package derived from the class) or via `POST /api/classes/:id/enroll` — and a student created without a class starts with no package.
- Keep deployment wiring in the infra package, not in app code.
- Keep syllabus file parsing in the browser; the server only receives validated JSON module trees (`POST /api/syllabus-templates/:id/replace-content` applies the replacement as one atomic D1 batch).
- Keep the syllabus model split by context (issue #394): a template is `syllabus.class_id IS NULL`, a class curriculum is a copy with `class_id` set — `syllabus.class_id` is the single source of truth for the class ↔ curriculum relation, while `class.syllabus_id` is a derived column written only through `apps/server/src/lib/syllabus-curriculum.ts`. Routes are context-scoped (`/api/syllabus-templates/...`, `/api/classes/:id/curriculum/...`); the legacy `/api/syllabi/...` alias paths were removed in phase 8 (issue #401).
- Keep the assignments router mounted inside the kernel route tree (`kernel.route("/assignments", ...)`) so the kernel's Origin + JSON CSRF guard covers every assignment write; never mount it standalone.
- Keep every rich-text surface rendering through the single DOMPurify sink `RichTextBody` in [packages/ui/src/components/assignments/rich-text-body.tsx](../packages/ui/src/components/assignments/rich-text-body.tsx) — the security boundary is having exactly one `dangerouslySetInnerHTML` site, so never add another. The authoring HTML fields are now nine (#420/#424): the original seven of the assignment contracts (`prompt`, `passage`, `intro`, `transcript`, `note`, question `explanation`, assignment `description`) plus library `questions[].explanation` and `groups[].instruction` from `packages/api/src/library-contracts.ts`. `cuePoints` deliberately stays plain text: its contract is one cue per line, not formatted prose.
- Keep the full security-header suite on every host; only the `Content-Security-Policy` header is dropped for localhost/loopback dev HTML (the dev worker serves Vite-transformed HTML whose inline React-Refresh preamble cannot pass `script-src 'self'`), while prod and staging keep it.
- Keep unknown web paths answering HTTP 404 from the asset worker (branded SPA shell for browser navigations, plain text otherwise); never serve unknown paths as a 200 SPA rewrite.
- Keep auth topology (origins, cookie domain, cookie namespace prefix) derived from `APP_DOMAIN` in the topology modules. Because staging is a subdomain of the prod apex, browsers send prod's parent-domain session cookie to the staging API too; any non-prod member of that cookie zone must namespace its auth cookies (`teacheros-staging`) so the foreign cookie cannot shadow its sessions, while prod and local stay on the default `better-auth` names.
- Keep the account-role separation in force across all layers: on the unified LMS origin (`lms.<domain>`), sign-up classifies `user.role` by allowlist (`ADMIN_EMAILS > TEACHER_EMAILS > student` in [packages/auth/src/index.ts](../packages/auth/src/index.ts)); standalone dev/legacy origins still stamp role from Origin/OAuth state and reject cross-app sign-ins (`ROLE_MISMATCH`); and the API middlewares remain the security boundary (`bootstrapMiddleware` blocks `student`/`admin` roles, `requireStudent` blocks non-student roles, `requireAdmin` enforces `role === "admin" ∧ email_verified ∧ email ∈ ADMIN_EMAILS`) because all portals share one `lms.<domain>` origin and session cookie zone.
- Keep the payment ledger (`payment_transaction`) the single source of truth for `invoice.paid_amount` (#320): every inbound amount goes through `ingestTransaction` (idempotent on `UNIQUE(provider, provider_txn_id)`), and `paid_amount` is always recomputed from `SUM(matched)` — never incremented in place. Only assign/matching writes touch it; no route lets a client write `paid_amount`/`status` directly.
- Keep every binary upload into `MediaStore` / R2 validated by the three-layer gate (`sanitizeMediaFileName` + extension ↔ `Content-Type` + 64-byte magic-byte prefix) before `store.put` or a credit hold (#676/#681). The 64-byte check authenticates the format header only — it is defense-in-depth, not content assurance: the isolation boundary on replay remains the DB-stored `Content-Type` plus `X-Content-Type-Options: nosniff` and CSP `sandbox`. Never accept a file whose declared size differs from the streamed byte count; reject with the route's own error codes (`415` unsupported, `400` size mismatch) and abort the source stream on every rejection path.
- Keep transfer-matching tenant-scoped: a code is only matched against invoices of the org that owns the receiving `bank_account_xid`; a valid code of another org lands as `foreign_code` under the receiving org with `content`/`payment_code` redacted in DTOs.
- Keep the Bank Hub webhooks and the public pay endpoint mounted outside `/api/*` (bootstrap middleware 403s student roles there and the pay page must work signed-out); webhook auth is the `X-Secret-Key` / `Apikey` headers compared with `timingSafeEqual`. SePay retries only on network errors, so the IPN handler acks even on org-resolution API failure (reconciliation recovers) and answers `{"success": true}` for anything it ignores.
- Keep the admin console outside the kernel tree: `apps/admin` is served under the unified LMS at `lms.<domain>/admin` (standalone dev port 8004) and its API lives at `/api/admin` with its own gate — `requireAdmin` re-checks `role === "admin"` ∧ `email_verified` ∧ email ∈ `ADMIN_EMAILS` on every request, writes are CSRF-checked against `ADMIN_ORIGINS`, and the admin role never bootstraps org/membership on the kernel tree (403 `ACCOUNT_ADMIN_ROLE`) — never mount admin routes under `/api/kernel` and never let kernel bootstrap apply to admin sessions.
- Keep single-org teacher access enforced by policy (#513): when `TEACHER_EMAILS` is non-empty (required fail-closed on production via `resolveTeacherEmails`), `databaseHooks.user.create.before` blocks teacher sign-ups outside the allowlist (`TEACHER_SIGNUP_FORBIDDEN`) and `bootstrapMiddleware` blocks non-allowlisted teacher sessions on every kernel request with 403 `ACCOUNT_TEACHER_NOT_ALLOWED` before any `organization`/`membership` row is created, while keeping the multi-org schema (`organization`, `membership`, `orgId`) intact.
- Keep the student portal org selector fail-closed: the client-supplied org hint is validated against the signed-in email's profiles in `createStudentGuard` ([apps/server/src/routes/student.ts](../apps/server/src/routes/student.ts)) and rejected with 403 `STUDENT_ORG_MISMATCH` rather than falling back to a default org, so stale client state can never read or write the wrong tenant. Only `GET /api/student/orgs` stays outside that rejection so [apps/student/src/lib/query-client.ts](../apps/student/src/lib/query-client.ts) and [apps/student/src/lib/student-org-storage.ts](../apps/student/src/lib/student-org-storage.ts) can recover stale read state, while writes are never auto-retried across organizations.
