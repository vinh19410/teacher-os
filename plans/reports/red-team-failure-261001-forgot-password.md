## Finding 1: `sendResetPassword` throw bị better-auth nuốt — D5/RT3/Task 1.2 bước 3/Task 1.3 test 3 dựa trên tiền đề sai
- **Severity:** Critical
- **Location:** plan.md D5 + RT3; Phase 1 Task 1.2 bước 3 ("ném lỗi ra để better-auth trả lỗi cho client"); Task 1.3 bước 6 (test `mailer rejection ... is not success`)
- **Flaw:** Endpoint `/request-password-reset` gọi `sendResetPassword` qua `ctx.context.runInBackgroundOrAwait(...)`. Hàm này bọc `try { await promise } catch (e) { logger.error(...) }` — mọi rejection bị log rồi bỏ, endpoint luôn `return ctx.json({status:true})`. Khi `advanced.backgroundTasks.handler` được set thì còn bị `promise.catch(...)` + chạy nền. Khác với `/send-verification-email`, nơi better-auth tự `await` trực tiếp kèm comment "runInBackgroundOrAwait may defer work or swallow errors (see #8757)". Plan nhầm hai đường này giống nhau (plan còn dựa vào comment email-verification.mjs:109-117 của repo cho đường resend).
- **Failure scenario:** Resend down/timeout 10s -> `createResendMailer` reject -> better-auth log "Failed to run background task" -> client nhận 200 -> UI hiện "nếu có tài khoản thì đã gửi" trong khi không thư nào được gửi. Đúng cái lỗi RT3 muốn tránh. Test 3 (`status khác 200`) sẽ FAIL ở bước verify của Phase 1; theo Failure Protocol implementer phải dừng + gọi kongming -> đốt budget Phase 1 ngay từ đầu. Nếu implementer "sửa" test cho xanh thì mất bằng chứng cho Success Criteria.
- **Evidence:** `better-auth@v1.6.27:packages/better-auth/src/api/routes/password.ts:134-146` (gọi `runInBackgroundOrAwait` rồi luôn trả `status: true`); `better-auth@v1.6.27:packages/better-auth/src/context/create-context.ts:408-426` (try/await/catch chỉ log; nhánh handler dùng `promise.catch`); `better-auth@v1.6.27:packages/better-auth/src/api/routes/email-verification.ts:68-70` (comment cảnh báo + await trực tiếp, đối chứng); `packages/auth/src/index.ts:123-155` hiện chỉ có `emailAndPassword: {enabled}` (123) và `emailVerification` (126), không `advanced.backgroundTasks`; `packages/auth/src/auth-verification-email.test.ts:97-140` (test resend chứng minh đường KHÁC, không áp dụng cho reset).
- **Suggested fix:** Sửa D5/RT3/test 3 trước khi cook: hoặc (a) chấp nhận fail-open có chủ đích cho reset, đổi test 3 thành "mailer rejection vẫn trả 200 và ghi `console.error`/structured log không chứa url/token", UI vẫn báo lỗi cho lỗi mạng/non-200 (429, 400 `RESET_PASSWORD_DISABLED`); hoặc (b) nếu bắt buộc propagate thì phải tự bắt lỗi trong `sendResetPassword` vào biến theo request (ví dụ WeakMap keyed theo `request` được truyền làm tham số thứ 2) rồi throw trong `hooks.after` cho path `/request-password-reset` — nhưng xem Finding 2 trước vì cách này tạo oracle liệt kê tài khoản. Không được để test đang "mong đợi 500" mà không chứng minh trước bằng một spike 5 phút.

## Finding 2: Muốn propagate lỗi mailer thì tự phá D5 chống liệt kê (oracle trạng thái + oracle thời gian)
- **Severity:** High
- **Location:** plan.md D5 ("Không tiết lộ email có tồn tại" + "Lỗi mailer không được nuốt"); Phase 1 Task 1.2 bước 2-3; Phase 3 Task 3.2 bước 4 (unknown email)
- **Flaw:** Hai yêu cầu của D5 mâu thuẫn. (1) User tồn tại: handler `await` mailer (Resend fetch, timeout 10s) rồi mới trả; user không tồn tại: trả ngay sau một lần lookup giả. Chênh lệch thời gian = tốc độ gọi Resend (hàng trăm ms) — better-auth chỉ mô phỏng DB lookup, không mô phỏng mail. (2) Nếu hiện thực kiểu "throw cho non-200" thì khi mailer lỗi, email tồn tại -> 5xx, email không tồn tại -> 200: oracle trực tiếp. Test unknown-email trong plan chỉ so status 200==200 trong điều kiện mailer healthy nên không bắt được cả hai.
- **Failure scenario:** Kẻ tấn công quét danh sách email giáo viên/học viên, đo latency `/api/auth/request-password-reset` (hoặc kích mailer lỗi) -> phân biệt email có tài khoản. Plan ghi Success Criteria "không lộ" nhưng chỉ kiểm bằng mail log.
- **Evidence:** `better-auth@v1.6.27:packages/better-auth/src/api/routes/password.ts:100-112` (nhánh user-not-found trả ngay), `:134-146` (nhánh có user await mailer); `packages/auth/src/mail/mailer.ts:33-35` (Resend `fetch` với `AbortSignal.timeout(10_000)` — chờ tối đa 10s inline trong request Worker); `apps/server/src/index.ts:73` (authHandler chạy inline, không waitUntil).
- **Suggested fix:** Chọn một: fail-open + log (Finding 1a) cộng khuyến nghị đưa gửi mail ra nền bằng `advanced.backgroundTasks.handler` gắn `ctx.waitUntil` của Worker để cân bằng thời gian (cần plumbing `executionCtx` vào `createAuth`, ghi rõ trong Phase 1); thêm test đo "unknown email và known email cùng không phụ thuộc mailer latency" bằng mailer giả sleep 300ms (assert known không chậm hơn unknown quá ngưỡng, hoặc assert handler không await mailer).

## Finding 4: Thứ tự deploy server/web/student và rollback không được lên kế hoạch — link trong mail trỏ vào route chưa tồn tại
- **Severity:** High
- **Location:** plan.md (không có mục deploy/rollback); Phase 2 Task 2.1; Phase 1 + Phase 2 là hai bề mặt deploy độc lập
- **Flaw:** Link mail là `${BETTER_AUTH_URL}/api/auth/reset-password/<token>?callbackURL=<origin>/reset-password`, rồi 302 sang `/reset-password?token=...` của web/student. Plan không nêu thứ tự phát hành. Nếu server (Phase 1) lên trước web: mọi mail reset phát hành trong cửa sổ đó trỏ tới `/reset-password` mà web worker không công nhận — worker trả HTTP 404 (shell + status 404), TanStack Router hiện NotFound. Token đã tiêu hao một lần phát hành, mail đã gửi, user không biết. Rollback web (hoặc rollback server rồi redeploy) cũng làm các mail đang ở hộp thư (hạn 1h) chết như vậy; không có runbook. Ngược lại web lên trước server: `request-password-reset` trả 400 `RESET_PASSWORD_DISABLED` -> UI báo "Couldn't send" (chấp nhận được nhưng nên có trong plan). Student worker: SPA fallback theo `Accept: text/html` nên không 404, nhưng teacher thì có.
- **Failure scenario:** Release v0.0.11 deploy server trước (thứ tự thường do alchemy stack), giáo viên xin reset trong 5 phút đó -> mail tới -> bấm -> trang 404 "không tìm thấy"; hỗ trợ không truy được nguyên nhân vì mail log của prod không ghi. Cũng: dev server vite có middleware 404 giống worker, nhưng e2e chỉ chạy vite nên không bao giờ thấy lỗi này.
- **Evidence:** `apps/web/src/worker.ts:106-137` (route không nằm trong `isValidAppRoute` -> 404 shell), `apps/web/src/routes-matcher.ts:4-21` (hiện chỉ có `/login`, không có hai route mới), `apps/web/vite.config.ts:49` (dev middleware cùng matcher, e2e che khuất lỗi worker), `apps/student/src/worker.ts:73-94` (student fallback SPA, bất đối xứng với web), `better-auth@v1.6.27:packages/better-auth/src/api/routes/password.ts:132-133` (URL dựng từ `ctx.context.baseURL` + redirectTo của client).
- **Suggested fix:** Thêm vào Phase 3 (hoặc plan.md) một mục "Deploy order": web + student trước (route + matcher đã có), server sau; rollback server trước web. Ghi rằng token reset còn sống 1h sau rollback và link sẽ vẫn tới web đã có route. Thêm bước verify sau deploy: `curl -sI https://<web>/reset-password` trả 200 (không 404) và `curl` GET `/api/auth/reset-password/x?callbackURL=<web>/reset-password` trả 302 tới `?error=INVALID_TOKEN`.

## Finding 5: Rate limit mặc định 3 request/60s/IP trên `/request-password-reset` — bẫy double-click, NAT lớp học, và test không thể quan sát
- **Severity:** High
- **Location:** Phase 2 Task 2.2 bước 5-6 / Task 2.4 bước 4 (xử lý lỗi gửi); Phase 1 Task 1.3 (không test limiter); Phase 3 Task 3.2 (e2e chạy non-production)
- **Flaw:** better-auth có special rule cố định cho path `/request-password-reset`: window 60s, max 3, key theo IP+path, bật khi `isProduction`. Plan không đề cập: (a) người dùng bấm lại "Email me a reset link" khi chưa thấy mail (hành vi tất yếu) -> request #4 trong 60s nhận 429; UI chỉ có toast generic "Couldn't send the reset email" (web) và chuỗi cố định "Không gửi được email đặt lại" (student) khiến người dùng nghĩ mail hỏng; (b) cổng học viên: cả lớp/trung tâm sau một NAT dùng chung bucket 3 req/phút; (c) nếu runtime không suy ra được IP, mọi người dùng chung một bucket toàn cục (`NO_TRUSTED_IP_KEY`) — một bot 3 req/phút khoá reset password của toàn hệ thống; limiter là in-memory per-isolate (`apps/server/src/index.ts:24-27`) nên hành vi còn chập chờn theo isolate. (d) Unit/e2e chạy non-production nên `enabled=false`: toàn bộ nhánh này không có test, không có copy.
- **Failure scenario:** Giờ cao điểm đầu tháng, 10 học viên cùng wifi trung tâm bấm "Quên mật khẩu" -> người thứ 4 trở đi bị 429 "gửi thất bại" trong cả phút; ai bấm lại sẽ kéo dài tình trạng. Hoặc không có IP header -> bucket chung.
- **Evidence:** `better-auth@v1.6.27:packages/better-auth/src/api/rate-limiter/index.ts:527-538` (rule `/request-password-reset` window 60 max 3), `:392-396` (fallback bucket chung khi không có IP), `better-auth@v1.6.27:packages/better-auth/src/context/create-context.ts:355` (`enabled: options.rateLimit?.enabled ?? isProduction`); `apps/server/src/index.ts:24-27` (comment xác nhận in-memory limiter đang hiệu lực, bursts thấy 429); `apps/e2e/src/boot.ts:74-83` (e2e `createAuth` không bật rateLimit).
- **Suggested fix:** Thêm vào Phase 2: nút submit disabled sau thành công + countdown ≥60s ("Gửi lại sau Ns"), map HTTP 429 -> copy riêng ("Bạn thử quá nhanh, đợi 1 phút") ở cả hai app; thêm một test component 429. Phase 1: một test với `rateLimit: { enabled: true }` cố định hành vi 429 ở request thứ 4 để biết chắc contract. Ghi vào Security Considerations: rủi ro bucket chung khi không có IP và quyết định chấp nhận.

## Finding 6: Xử lý lỗi `resetPassword` đồng nhất một câu "request a new link" — sai với lỗi còn retry được; double-submit sinh toast lỗi sau thành công
- **Severity:** Medium
- **Location:** Phase 2 Task 2.3 bước 3-6 (và 2.4 bước 5-7)
- **Flaw:** Token bị tiêu hao bằng `consumeVerificationValue` TRƯỚC khi hash/ghi mật khẩu; chỉ validate độ dài trả 400 TRƯỚC khi consume. Plan dùng một toast cố định "Request a new reset link" cho mọi lỗi: (i) lỗi mạng/5xx trước khi tới server -> token còn nguyên nhưng UI bảo xin link mới (và dính rate limit Finding 5); (ii) `PASSWORD_TOO_LONG`/`TOO_SHORT` do server (policy server khác `PASSWORD_MIN` client nếu đổi) -> token chưa consume nhưng UI bảo xin link mới. (iii) Double-click/Enter hai lần: request đầu thắng (200), request sau nhận `INVALID_TOKEN` 400 -> UI vừa hiện "Password updated" vừa toast đỏ (hoặc ngược thứ tự: toast lỗi rồi success). Plan không bắt buộc disable submit/guard `isSubmitting` hay dựa theo `error.code`. (iv) Lỗi giữa consume và `updatePassword` (DB hiccup D1) đốt token mà user chưa đổi được mật khẩu — copy "xin link mới" đúng ở case này nhưng không phân biệt được với (i)/(ii).
- **Failure scenario:** Giáo viên mạng chập chờn bấm Update, nhận toast "Request a new reset link", xin link mới -> 429 (Finding 5) -> kẹt, trong khi link cũ vẫn dùng được.
- **Evidence:** `better-auth@v1.6.27:packages/better-auth/src/api/routes/password.ts:280-299` (length check -> consume trước hash), `:301-320` (hash + updatePassword sau consume, không rollback token), `:277,299` (`INVALID_TOKEN` cho token đã dùng); `apps/web/src/components/auth/submit-button.tsx:9-28` (chỉ có `disabled`/`spinning`, caller phải truyền); `apps/web/src/lib/auth-error.ts:6-16` (`authErrorMessage` trả `message` server nếu có — cũng sẽ trả tiếng Anh trên UI student nếu dùng lại).
- **Suggested fix:** Task 2.3/2.4: submit disabled + `spinning` khi `isSubmitting`; chỉ coi là "link hỏng" khi `error.code === "INVALID_TOKEN"` (hoặc status 400 với code đó), các lỗi khác giữ form + toast "thử lại"; dùng chuỗi cố định tiếng Việt cho student thay vì `authErrorMessage`.

## Finding 7: RT5 và vai trò chéo cổng — "neutral" không đúng với hành vi thật (tạo credential cho tài khoản Google, reset từ sai cổng gây dead-end)

- **Location:** plan.md RT5; D2 ("đúng cổng đã xin"); Phase 3 Success Criteria "student ... không nhảy sang origin teacher"
- **Flaw:** (a) RT5 nói tài khoản chỉ Google "có thể không có credential" và coi như xong.
